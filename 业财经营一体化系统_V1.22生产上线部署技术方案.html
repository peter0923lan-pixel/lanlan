PRODUCTION DEPLOYMENT DESIGN

业财经营一体化系统
V1.22 生产上线部署技术方案

适用于 10–30 名公司飞书内部成员的日常使用场景。采用单可用区、允许人工恢复的务实架构，在不引入 Kubernetes 和双活集群的前提下，实现数据独立、权限可审计、可回滚和可恢复。

1. 范围与设计目标

已确认条件

  • 首批 10–30 名日常用户，主要为公司内部业务、财务和管理人员。
  • 仅公司飞书内部成员允许登录；不开放外部合作方账号。
  • 可接受单台应用服务器故障后的人工恢复，不要求自动切换或双活。
  • 业务数据包括合同、回款、收入、审计记录和合同附件，需可恢复、可追溯。

目标

  • 生产环境仅暴露 HTTPS 入口；API、数据库、OSS 均不直接对公网开放。
  • 应用故障时恢复目标：RTO ≤ 4 小时、RPO ≤ 24 小时；数据库误操作可按 RDS 备份窗口进行时间点恢复。
  • 任何发布均有版本号、发布人、变更说明、发布前备份和可执行回滚步骤。
  • 生产访问、登录、发布和关键业务操作均具备审计线索。

本期非目标

  • 不建设 Kubernetes、自动弹性扩缩容、跨地域双活或多活。
  • 不把飞书通讯录全量同步、审批流、机器人消息作为登录一期的前置条件。
  • 不允许通过 OSS 公共读链接直接访问合同附件。

2. 阿里云资源与采购清单

2.1 推荐配置

资源建议规格网络/安全要求说明
ECS 应用服务器通用型 g 系列，4 vCPU / 8 GiB；100 GiB ESSD；Ubuntu 24.04 LTS；按年订阅。位于私有 vSwitch；绑定 1 个 EIP 或经 ALB 暴露；安全组仅开放 443、堡垒机来源的 22。运行 Docker、Nginx、React 静态站、FastAPI、定时备份任务。阿里云对通用 Web/应用工作负载推荐通用型实例；g 系列采用 1:4 CPU/内存比。[ECS 选型]
RDS MySQLMySQL 8.0 高可用版，2 核 4 GiB 起，50–100 GiB ESSD；与 ECS 同地域同 VPC。仅创建 VPC 内网地址；白名单仅允许 ECS 安全组/私网段；开启 SSL 连接。建议购买。生产业务数据不建议继续部署在 Docker MySQL 卷中。预算极紧时可选基础版 2C4G，但发生实例故障的恢复能力较弱。
OSS标准存储私有 Bucket：bfm-prod-attachments；同地域。阻止公共访问；应用使用 RAM 角色最小权限访问；开启版本控制、SSE、访问日志。存合同附件和备份归档；OSS 私有 Bucket、版本控制和生命周期可降低误删与长期存储风险。[OSS Bucket 安全与生命周期]
公网与 HTTPS初期：EIP + Nginx；推荐域名 1 个、DV/OV SSL 证书。仅 443 公网入站；80 仅用于跳转 HTTPS/证书验证；启用 WAF/基础防护视预算选择。当前规模不强制购买 ALB；后续需双 ECS 时再引入 ALB。
堡垒机阿里云堡垒机基础版或企业现有堡垒机。禁止开发人员直接使用公网 SSH；所有 SSH 通过堡垒机账号与授权策略访问。用于运维访问控制、命令审计和离职回收。若企业已有统一堡垒机，可直接纳管这台 ECS。
监控与告警云监控 + ActionTrail；可选 SLS 日志服务。告警通知到运维群/邮件；操作日志保留至少 180 天。监控 CPU、内存、磁盘、容器健康、HTTPS 可用性、RDS 容量与备份失败。
成本取舍：若暂不采购 RDS，最低可将 MySQL 放在 ECS 独立数据盘中并做快照/逻辑备份，但这会使应用、数据库和附件故障域耦合，不建议用于正式财务经营数据。即使可接受人工恢复，也建议优先把预算留给 RDS 和 OSS。

2.2 需要由业务方/云账号管理员提供的前置条件

  • 阿里云账号或资源组权限：ECS、RDS、OSS、RAM、VPC、安全组、EIP、云监控、ActionTrail。
  • 生产域名，例如 bfm.company.com；域名 DNS 管理权限与 SSL 证书申请人。
  • 企业飞书管理员，能够创建/发布企业自建应用并配置可用范围。
  • 运维联系人、告警接收飞书群/邮箱、RDS 管理员与数据恢复审批人。
  • 生产环境管理员初始账号信息或由系统所有人现场设置的初始密码。

3.2 生产配置原则

  • 生产 .env 不提交 Git；使用服务器受限目录或阿里云 KMS/Secrets Manager 保存，文件权限为 600。
  • APP_SECRET_KEY、RDS 密码、初始管理员密码、飞书 App Secret、OSS 凭据全部使用独立随机强值；严禁使用当前示例默认密码。
  • API、RDS、OSS 的访问密钥不写入前端包、不写入仓库、不出现在构建日志；ECS 优先使用 RAM 实例角色取临时授权。
  • Nginx 加入 HSTS、X-Content-Type-Options、Content-Security-Policy、Referrer-Policy 等安全响应头；限制上传体积为 20 MB 左右。
  • 生产 Docker Compose 删除数据库公网端口映射；仅 Web/Nginx 接入 443。
生产服务关系（示意）
Internet → HTTPS 443 → Nginx(web) → /api/* → FastAPI(api)
FastAPI(api) → RDS MySQL（VPC 私网）
FastAPI(api) → OSS 私有 Bucket（ECS RAM 角色）
堡垒机 → SSH 22 → ECS（禁止直连公网 SSH）

4.2 堡垒机纳管要求

  1. 在堡垒机中创建目标资产：生产 ECS 私网 IP、SSH 端口 22、运维专用 Linux 账号 bfmops。
  2. 创建个人账号，不共享 root 密码；账号与企业身份绑定，离职立即回收。
  3. 授权分组：运维人员可登录并执行发布；开发人员默认仅允许只读日志命令；业务人员无需 SSH 权限。
  4. 开启会话录像和命令审计，保留至少 180 天；禁止上传未审批脚本和使用 root 直连。
  5. 主机上使用 sudo 白名单执行 docker compose、日志查看、健康检查和备份恢复脚本，避免直接使用 root。

5. 部署流程

5.1 一次性基础建设

  1. 在目标地域创建 VPC、私有 vSwitch；将 ECS 与 RDS 放入同一 VPC，RDS 不开公网。
  2. 创建 ECS（4C8G/100G ESSD）、安全组、EIP、域名解析和 SSL 证书；配置堡垒机纳管。
  3. 创建 RDS MySQL 8.0，创建业务库 bfm_prod 和最小权限应用用户 bfm_app；启用自动备份、日志备份、SSL 和监控告警。
  4. 创建 OSS 私有 Bucket，开启阻止公共访问、版本控制、服务端加密、访问日志和生命周期；创建最小权限 RAM 策略并绑定到 ECS RAM 角色。
  5. 安装 Docker Engine、Docker Compose Plugin、git/镜像拉取工具；创建 /opt/bfm、/opt/bfm/releases、/opt/bfm/backups 等受限目录。

5.2 生产适配改造（上线前必须完成）

改造项具体内容验收条件
生产 Compose拆出 compose.prod.yaml；移除 db 服务和 3306 映射；API 使用 RDS DATABASE_URL；Web 仅暴露 Nginx。docker compose -f compose.prod.yaml up -d 后 API 健康、前端可访问，RDS 无公网入口。
OSS 附件适配新增对象存储适配层；合同附件元数据继续存 MySQL，文件存 contracts/{contract_id}/{uuid}；下载前必须再次鉴权。上传、下载、作废、版本化均可用；Bucket 无匿名读取。
飞书登录按第 6 节接入 OAuth 2.0；保留本地管理员“应急登录”开关，仅限堡垒机/VPN 环境或灾备流程使用。在企业飞书范围外的账号无法登录；登录后本地角色正确生效。
安全加固HTTPS、安全响应头、限流、登录审计、错误脱敏、上传文件白名单和恶意文件扫描（可后置）。安全扫描无高危公网暴露；异常登录、登录失败和关键操作有审计。

5.4 回滚原则

  1. 前端/API 代码异常：切回上一已验证镜像标签，重新启动应用容器；不回滚数据库。
  2. 包含数据库迁移的版本：优先使用“向前修复”迁移；只有已验证 downgrade 且无新增业务数据时才允许回退数据库结构。
  3. 数据误操作：由业务管理员批准后，优先恢复到新 RDS 实例并导出/核对差异，禁止直接覆盖生产库。

6. 飞书登录与安全校验技术方案

6.1 设计原则

  • 飞书只负责证明“该用户是企业内哪个成员”；本系统继续负责本地用户状态、角色、数据范围和审计。
  • 登录主键使用飞书稳定用户标识（建议 open_id，必要时同时保存 user_id），不以手机号或邮箱作为唯一认证依据。飞书官方也明确提示手机号/邮箱可能不是实时验证信息。[飞书用户信息接口]
  • 仅授予登录和读取最小必要身份信息权限；不申请通讯录全量读取、聊天记录等无关权限。
  • 飞书 access token 不作为本系统会话；后端验证身份后签发短期本系统 JWT，前端仅将其放入 sessionStorage。

6.2 飞书开放平台配置

  1. 由企业飞书管理员创建企业自建应用，配置网页应用主页为 https://bfm.company.com。
  2. 在“安全设置”中配置固定回调地址：https://bfm.company.com/api/v1/auth/feishu/callback；飞书仅允许已配置回调地址通过安全校验，动态路由不受支持。[飞书重定向 URL 配置]
  3. 按登录所需范围申请最小权限，发布应用，并将可用范围限定为公司内部目标部门/全员；未被纳入可用范围的成员在飞书侧无法取得授权码。
  4. 将 App ID、App Secret 通过密钥管理交付给后端，不传递给浏览器，不写入代码库；应用发布变更由飞书管理员审核。

6.3 后端登录流程

1. 发起登录浏览器访问 /auth/feishu/login
→
2. CSRF 防护后端生成随机 state，绑定 HttpOnly/SameSite cookie，5 分钟过期
→
3. 飞书授权飞书回调携带一次性 code 与 state
→
4. 服务端校验校验 state、交换 token、读取身份信息
→
5. 本地授权匹配/创建用户、检查启用状态和角色，签发本系统 JWT

6.4 必做安全控制

控制点实现要求
回调地址后端使用配置中的固定 redirect_uri；绝不接受请求参数任意指定回调地址，防止开放重定向。
state / PKCEstate 至少 256 位随机值、单次使用、5 分钟过期，与浏览器会话绑定；采用 OAuth 标准 PKCE（S256）以降低授权码截获风险。
授权码只允许服务器向飞书 token 接口交换；授权码有效期 5 分钟且仅能用一次，回调后立即作废本地 state。[飞书 Token 接口]
企业成员限制飞书应用可用范围限制 + 后端本地白名单/部门映射双重校验。飞书身份存在但本地未授权时显示“未被授予系统访问权限”，不自动授予管理员。
会话本系统 JWT 有效期建议 2 小时；前端 sessionStorage；退出时清除；关键操作仍由后端基于本地角色鉴权。
防暴力与审计对登录入口限流；记录成功/失败、飞书标识、IP、User-Agent、请求 ID、时间和失败原因，不记录 access token 或 App Secret。
本地应急登录保留本地密码登录仅作为飞书故障应急开关，默认关闭；启用需两人审批、限制 VPN/堡垒机来源、完成后立即关闭并审计。

6.5 数据模型与验收

在现有 users 表中新增 auth_source、feishu_open_id（唯一）、feishu_user_id、last_login_at、last_login_ip；建立登录审计表或复用审计日志。飞书登录成功后，必须根据本地用户的 role、is_active 和数据范围执行访问控制，绝不能将飞书部门/职位直接当作系统管理员权限。

验收红线：不可在前端保存 App Secret、飞书 user_access_token 或 refresh_token；不可仅按邮箱/手机号匹配管理员；不可让未纳入飞书应用可用范围或本地未启用的账号进入系统。

→
代码评审合并 develop，自动构建
→
预发验证同版本镜像 + 脱敏数据
→
生产发布标签、备份、健康检查、UAT

7.2 代码仓库与版本规则

  • 将当前项目根目录初始化为私有 Git 仓库并托管至 GitHub Enterprise、GitLab 或阿里云 Codeup；.env、备份、真实附件和数据库导出不得提交。
  • 分支：main（生产）、develop（预发）、feature/xxx（需求）、hotfix/xxx（线上紧急修复）。
  • 采用语义版本：v1.22.0（稳定发布）、v1.22.1（缺陷修复）、v1.23.0（兼容的新功能）。每个 Tag 对应一套不可变 API/Web Docker 镜像。
  • 每次 PR 必须包含：变更说明、影响模块、数据迁移说明、测试结果、回滚方式和 UAT 用例；涉及合同/回款/收入口径必须由业务负责人确认。

7.3 从开发电脑到服务器的推荐路径

阶段执行位置产物/门禁
本地开发开发电脑功能分支；后端测试、前端构建、Docker 本地验收。数据库变更必须新增 Alembic migration。
合并与构建CI（GitHub Actions / GitLab CI / Codeup Pipeline）运行 pytest、ruff、tsc、vite build；构建 API/Web 镜像，镜像标签为 Git commit SHA 与版本号；推送至阿里云 ACR。
预发部署预发 ECS / Docker Compose同一版本镜像；独立预发 RDS/OSS；通过健康检查与核心 UAT 后生成发布批准。
生产发布堡垒机/受控 CI Runner先执行 RDS 备份校验和发布前快照，再拉取指定版本镜像、启动、检查迁移和健康接口。
发布后业务 + 运维完成飞书登录、合同、附件、回款、收入等冒烟验证；记录发布结论和镜像 Tag。

7.4 CI/CD 安全要求

  • CI 使用专用最小权限 RAM 用户/角色推送 ACR、触发部署；生产密钥从 Secrets Manager 注入，不能在 CI 日志打印。
  • 生产部署默认人工批准；只有 main Tag 能部署生产。紧急 hotfix 需补充发布记录。
  • 镜像保留策略：生产稳定镜像至少保留最近 10 个版本与最近 90 天；禁止用 latest 作为生产唯一部署标识。
  • 发布时保留上一个版本目录和镜像 Tag。应用代码回滚不自动回退数据库迁移。

8. 自动备份、恢复与演练

8.1 三层备份策略

对象机制频率与保留建议恢复方式
RDS MySQLRDS 自动全量备份 + 增量日志备份；发布前手工备份/恢复点。每日低峰全量；至少保留 30 天；月度归档 12 个月。RDS 支持全量和增量日志备份，云盘实例备份保留范围可配置。[RDS 自动备份]优先恢复到新 RDS 实例核对，再切换连接；误操作按时间点恢复。
OSS 附件Bucket 版本控制 + OSS/Cloud Backup 定时备份。版本保留 90 天；每日备份，保留 30 天；长期归档按合规要求设置。恢复指定对象版本或从 OSS Backup 恢复。OSS 版本控制可防止误覆盖/误删。[OSS 版本恢复]
ECS 与配置云盘自动快照 + Git/ACR 中的代码和镜像。每日 02:00 快照，保留 7–14 天；重大变更前手工快照。新 ECS 从镜像/部署包重建；配置从密钥管理和受控备份恢复。ECS 云盘不会自动备份，必须绑定自动快照策略。[ECS 自动快照]
发布与审计Git Tag、CI 工件、ActionTrail、堡垒机会话和系统审计日志。发布记录永久保留；日志至少 180 天。用于定位谁在何时发布/变更，不替代业务数据恢复。

8.2 自动化任务

  • 每日检查 RDS 最近一次备份状态、OSS 备份任务、ECS 快照和 API 健康；失败即通知运维飞书群。
  • 每日导出 RDS 逻辑备份到 OSS 作为额外可移植副本（加密、私有、保留 30 天）；此副本不替代 RDS 时间点恢复。
  • 每周清理过期容器镜像和临时文件；不得清理当前生产或回滚版本镜像。
  • 每月执行一次恢复演练：恢复一份 RDS 备份到隔离实例，校验合同数、附件元数据数、抽样下载附件和应用健康接口。

8.3 恢复决策

事故第一处置恢复路径
应用容器不可用检查 Nginx/API 健康、日志、磁盘和 RDS 连接。重启容器；无效则切回上一镜像 Tag；ECS 故障时新建 ECS 并使用受控部署包重建。
数据库误删/错误更新立即停止相关写操作，保留证据，业务管理员批准恢复。按 RDS 时间点恢复到新实例，比较差异后定向修复或切换。
附件丢失/误作废根据合同附件记录定位存储键和版本。从 OSS 历史版本/备份恢复对象；数据库记录按审计流程处理。
飞书登录故障检查飞书应用可用范围、回调地址、证书、state 校验和开放平台状态。按应急流程、审批后短时开启受限本地管理员登录；故障恢复后关闭并复盘。

9. 上线验收清单

  • 域名全站 HTTPS 正常，HTTP 自动跳转；安全组无 MySQL/API 公网端口。
  • RDS 位于私网，应用仅通过最小权限账号和 TLS 访问；已验证自动备份和一次恢复演练。
  • OSS Bucket 为私有、阻止公共访问、版本控制/加密/日志已开启；上传和经鉴权下载正常。
  • 堡垒机中可见生产 ECS，个人账号授权、生效时间、命令审计和会话录像均已确认。
  • 飞书内授权用户可登录；飞书范围外或本地未授权用户无法登录；角色和数据范围与本地授权一致。
  • 生产部署使用固定镜像 Tag；完成 API/Web 健康检查和合同、附件、回款、收入、驾驶舱的冒烟验证。
  • 已将部署、回滚、备份恢复、密钥轮换、告警联系人与值班责任写入交付文档。
  • 已完成一次“代码回滚”和一次“RDS 恢复到隔离实例”的演练，并记录耗时和问题。
最终建议：当前规模最值得投入的不是多台应用服务器，而是 RDS、私有 OSS、堡垒机审计、飞书单点登录和恢复演练。这五项能够显著降低经营数据丢失、人员越权和上线不可回退的风险。
